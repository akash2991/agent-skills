# agent-brain

This repository is the **source** of an injectable agent organization, and it is also **run by that organization**. The brain is injected into itself, so the rules below apply to the work of changing them. That recursion is the point: the organization improves itself by using itself, and friction met while doing real work is what tells us what to change.

This file and `CLAUDE.md` are the same contract for different harnesses. Change both, or neither.

The loop, and the invariants that keep it from eating itself, are in the `self-improvement` skill. Read it before changing anything here. The short version:

- **The root sources are the only truth.** `.agent-brain/`, `.claude/skills/`, `.claude/agents/`, and `.claude/commands/` in this repository are generated by `npm run inject:self` and are git-ignored. Editing them is lost work.
- **A rule takes effect at the next injection, not on save.** The session that changes a rule is still bound by the version it started under, so a change can land safely while work is in flight.
- **Guards tighten, never loosen.** Weakening the CEO lock, a budget guard, the review gate, the definition of done, the specialists-only rule, the escalation ladder, the observability privacy boundary, or the checks is a decision for the user, not an internal review. A self-modifying system can always make a task easier by relaxing the rule that made it hard; that is exactly what must not be available.

`Goal.md` holds the owner's running requirements, numbered by update. It is the specification of record. Never edit it.

## Working here

Start a session with `/brain-init`, the same way you would in any project the brain is installed in. Requests route through the CEO, which admits or parks them against the budget. This repository has two services, each with documents under `.agent-brain/services/`:

| Service | Covers | Personas |
|---|---|---|
| `brain-org` | `org/`, `agents/`, `skills/`, `references/`, `agents-reports/`, `templates/` | `org-principal-engineer`, `org-staff-engineer`, `org-code-reviewer` |
| `brain-platform` | `control-plane/`, `scripts/brain/`, the checks, CI | `backend-principal-engineer`, `backend-staff-engineer`, `backend-code-reviewer` |

The flow here is the flow minus a named set of exemptions the owner authorized: no PRD, no HLD, a small `LLD.md` per service instead, design review only when a change crosses services or touches a guard, and sprints only when work is large enough to need slicing. Intake, budgets, specialists-only, code review, tests, verification, and the guard rule all still apply. The list is in the `self-improvement` skill and nowhere else, it may only be widened by the user, and **it never applies in a repository the brain was injected into.** Those follow every step.

This repository's own stack may also differ from the stack it enforces: plain Node JavaScript and one HTML page here, Node with TypeScript and React with TypeScript in every injected project. That is recorded as a decision, not a gap to close.

## What produces what

```
org/         ──┐                                      ┌──▶ build/product/<tool>/ ──▶ inject      ──▶ a project
agents/      ──┤                                      │    (the finished organization)
skills/      ──┼──▶ validate ──▶ select ──▶ build ────┤
control-plane/ ┤                                      └──▶ build/self/<tool>/    ──▶ inject:self ──▶ this repository
templates/   ──┘                                           (adds the brain-development roles, omits the ones we have no surface for)
```

Two builds from one source, both under `build/`. The **product** build carries the finished organization and is what every other repository receives. The **self** build adjusts it for this repository through `self` in `manifest.json`:

- `self.add` carries the artifacts that exist only to change the brain: the `self-improvement` skill and the three `org-*` personas. A project consuming the brain never sees them, and `npm run validate` fails if anything in the product set references one, because that reference would dangle there.
- `self.omit` drops roles this repository has no surface for: the three mobile personas and the web performance auditor. `security-auditor` is deliberately kept, because the brain handles credentials, reads local credential stores, serves HTTP, and has a privacy boundary on telemetry.

Edit the sources. Everything under `build/` is generated and git-ignored; never hand-edit it, and never edit an emitted `ORG.md`.

| Source | Holds | Emitted as |
|---|---|---|
| `org/NN-*.md` | the always-on organization, as ordered parts | one `ORG.md` plus the managed block in each tool's always-on file |
| `agents/*.md` | personas; discipline variants use `extends:` | a skill per persona, and a subagent file where the tool has them (never the CEO) |
| `skills/<name>/SKILL.md` | the flat skill dump; `category:` only groups the output | one directory per selected skill |
| `agents-reports/*.md` | one uniform report per role | `.agent-brain/agents-reports/` |
| `control-plane/` | SQLite schema, CLI, UI, usage hooks, adapters | `.agent-brain/control-plane/` |
| `references/*.md` | shared checklists and cross-cutting contracts | `.agent-brain/references/`, with skill links rewritten |
| `templates/` | what is stamped into a project: global docs, service docs, the entry command | global docs and service-doc template, plus `/brain-init` in each tool's command format |
| `manifest.json` | which skills, personas, and tools get built, plus `self.add` and `self.omit` for this repository | — |

## Commands

| Purpose | Command |
|---|---|
| Validate the sources, including the self set and the leak check | `npm run validate` |
| Product build | `npm run all` |
| Self build | `npm run all:self` |
| Inject into another repository | `npm run inject -- <path> [--targets a,b] [--dry-run] [--install-commands]` |
| Re-run the loop on this repository | `npm run bootstrap` (self build, then `inject:self`) |
| Import a skill from elsewhere | `npm run import -- <path> --category <category>` |
| Control-plane tests | `npm run test:control-plane` |
| Ship traces to Langfuse | `node .agent-brain/control-plane/brain.js export langfuse [--all] [--dry-run]` |
| Skill anatomy | `node scripts/validate-skills.js` |
| Trigger and routing evals | `node scripts/run-evals.js --min-rank1 80` |
| Reference links | `node scripts/validate-reference-links.js` |

CI runs all of these plus an inject-and-exercise smoke test. Node 22.5 or newer is required, for the built-in SQLite.

## Conventions

- **A skill** lives at `skills/<kebab-name>/SKILL.md` with `name`, `description` (what it does, then "Use when"), and an optional `category`. It follows [docs/skill-anatomy.md](docs/skill-anatomy.md): Overview, When to Use, a process section, Common Rationalizations, Red Flags, Verification. Every skill needs an eval case in `evals/cases/<name>.json`, or the eval run fails.
- **A persona** lives at `agents/<kebab-name>.md` and follows [docs/persona-anatomy.md](docs/persona-anatomy.md). It lists the only skills it may use, and it carries **no model or effort**: those are per-task decisions recorded in the control plane, and the linter rejects them in frontmatter.
- **The organization's rules** live in `org/`, one topic per numbered part. Add a part rather than growing one.
- **Shared material** goes in `references/` when more than one skill or persona needs it; a skill's own supporting file stays in `skills/<name>/references/`.
- **Never duplicate content** between a skill, a persona, and a reference. Point at the one that owns it.
- **Skill links to shared references** are written `../../references/<file>.md`; the build rewrites them to the injected copy.

## Boundaries

- **Always** run `npm run all` after changing a source, and `npm run bootstrap` before starting a session that should use the change. Add an eval case with a new skill.
- **Always** keep `Goal.md` untouched, and treat its updates as the requirements they are.
- **Never** hand-edit anything under `build/`, or an emitted `ORG.md`.
- **Never** put a model or effort on a persona, or reintroduce a per-persona allowlist.
- **Never** add a slash command that starts a persona or a skill directly: in this organization every request routes through the CEO, and `/brain-init` is the only command.
- **Always** name a command `brain-<something>`. Commands land in a directory shared with the project and its other tools, so an unprefixed name is a collision whose loser is silently whichever loads second. The validator enforces it.
- **Never** let a product artifact reference a self-only one. Put brain-development machinery in `self.add`, and keep the universal behaviour (report friction upward) in the rules that ship.
- **Ask first** before deleting material that is not clearly a relic of the upstream fork, and before changing a validator's contract rather than the code it checks.
