Orchestrator: high-level design

One agent session takes the user's requests and never does the work. For each request it starts a new worker session, resumes a recorded one, or messages a running one, each in its own Herdr tab, and it keeps every session in a SQLite record.

State merged to main 16fff02 Tickets FAC-29 to FAC-33 Source skills/orchestrator/ Schema v3

The question this page answers: how does the orchestrator route work, what guarantees does it keep, and why is it about 1,700 lines when the pattern it follows is simple?

Short answer: the agent makes one judgment per request: new, resume, relaunch or send. One CLI does every exact step against a SQLite record and Herdr. The first version had 1,041 lines. Findings from 29 review rounds added launch rollback, prompt-delivery tracking and race fencing, which brought it to 1,702.

Goals and boundaries

In scope

  • Route every work request to exactly one session: new, resume, relaunch or send.
  • Keep each line of work in its own session, and bring related work back to the session that already has the context.
  • Record each decision with its reason, the sessions considered, and its outcome. The decision model (FAC-28) will learn from this.
  • Record each worker's prompts, compactions and status through hooks, and keep a summary the worker writes itself.
  • One orchestrator per project. A second one is read-only.

Out of scope

  • Doing work. The orchestrator never reads or edits project code, tickets or PRs.
  • Sessions the user started by hand. They have no hooks, are not in the record, and are never touched.
  • Supervising workers: no heartbeat, no polling, no merge pipeline. The user asks for status when they want it.
  • Parallel subagents inside one task. That is herdr-fanout, used by a worker.
  • Tracking whether a worktree still exists, or which session uses it. A later conversation gets the worktree only as a hint.

    State machines

    The record has three independent pieces of state per session. Placement, rollback, hook events and migrations each run as one transaction. Single updates (report, resolve, reopen) are single statements under SQLite's busy timeout.

    Session status

    A resolved session is never resumed. Related work starts new with --from. resolve, reopen and report --resolved|--open accept any status, superseded included. Setting a session open bumps its succession. A child supersedes only an open (or already superseded) parent, and records the parent_generation it superseded. A rollback reopens the parent only if no other child in that generation has, or may have, a worker.

    Held prompt

    A prompt leaves the list once it is accepted or dropped. One left in sending by a crash reads as unknown. A prompt of unknown delivery is never resent or dropped automatically. send, deliver, resume and relaunch refuse until the orchestrator checks the tab and settles it.

    Worker placement

    Only the placement (tab and pane) is stored; waiting and uncertain are read from Herdr and the launch's result. An uncertain tab stays recorded and blocks launches of that session until the tab is gone or adopted. Before a launch, the CLI closes a leftover tab that has no agent and detaches one that now runs another conversation.

    Data model

    One SQLite file per project, in WAL mode, gitignored. Migrations run in one transaction under the write lock: v1 is the original schema, v2 adds outcomes, prompt order and supersession generations, and v3 adds the worktree and the project root.

    Contracts

    These are the rules the review rounds converged on. Each one is enforced by tests.

    Launch routing is transactional

    A placement, and the supersession of an open parent by a session's first worker, commit together. A rollback restores the session's identity and reopens its parent together. It reopens the parent only while the parent is still superseded and no other child in the same generation has, or may have, a worker.

    History is best effort

    Events and outcomes written after an action print a warning when they fail. They never change a command's result or the guidance it prints.

    No automatic resend or drop

    A prompt whose delivery is uncertain is never resent or dropped automatically. The orchestrator checks the tab and settles it; --resend sends it again even if it had arrived. A launch that certainly failed is retried as its error says: a failed new keeps its session and brief, and names resume S<id> without --request. If the tab closed but the record could not be restored, the error names the one retry that does not resend the request.

    Never two workers on one conversation

    An uncertain tab blocks launches of its session. Resume and relaunch refuse when Herdr cannot list running agents. A launch token stops a failed launch's late hook from changing the session's identity or compaction count.

    Hooks never disturb the session

    Claude's hook is a bounded command with a 10-second timeout; Pi's extension hands each event to a detached writer. Both print nothing, note a failure in a side log, and do nothing outside a session the orchestrator launched.

    The user's answers are the user's

    Trust, login and permission prompts are never answered for the user. stop closes a working or blocked worker only with --force, on the user's word.

    What the review rounds added

    • Launch rollback. Close the tab, restore identity, undo supersession, and mark an uncertain tab. launch() is 135 lines, and most of them handle failure.
    • The held-prompt state machine. pending / sending / unknown, plus deliver and settle.
    • Launch tokens and identity sequencing, so racing hook writers never apply a stale start.
    • Supersession generations and a migration backfill (FAC-31).
    • Git validation of reported worktrees and a protected checkout (FAC-33).

    Each item fixes a real failure a reviewer found. Together they turn a router into a small transaction system.
